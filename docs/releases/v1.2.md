# v1.2 — Driver panel and transport assignments

Release tags: `v1.0` marks the last student-only main commit (`00a7029`),
`v1.1` marks the manager-era baseline (`c364d8d`), and `v1.2` marks the driver release.
Historical tags are milestones, not recommendations to roll a migrated database backward.

Includes driver enrollment, dashboards and documents, admin driver exports, paired
transport assignments, searchable student/route selectors, cross-school assignments,
route capacity displays, school-edit fixes, and updated opt-in demo seeds.

## Production deployment checklist

Production Compose and real environment files are unchanged. Repository checks do not
verify the production database, server-local modifications, storage credentials, or CORS.

1. Check the server's `git status --short` before pulling. Preserve and review local
   modifications; do not force-reset them. Use `git pull --ff-only origin main`.
2. Take and verify a database backup and record the currently deployed commit/image.
3. Review new migrations `0042`–`0046`. Before applying `0042`, run this read-only
   query against the intended database:

   ```sql
   SELECT phone_number, count(*)
   FROM drivers
   WHERE phone_number IS NOT NULL
   GROUP BY phone_number HAVING count(*) > 1;
   ```

   Any returned rows block the new unique phone index. Resolve ownership manually;
   do not delete or merge driver records automatically. Existing legacy driver rows
   are preserved and new enrollment fields remain nullable.
4. Keep `SEED_DEMO_DATA=false`. Do not copy the local `.env` or local Compose file
   onto production. Install with the committed lockfile and build using actual
   production API/asset origins and existing deployment secrets. Use a deployment
   ID without dots (for example `release-v1-2`), not the dotted Git tag itself.
5. Apply migrations once through the existing guarded deployment workflow before
   starting the new API. `infrastructure/database/migrate-safe.sh --apply` requires
   `DATABASE_URL`, `DEPLOY_ENV=production`, `RELEASE_ID`, a verified `BACKUP_RECEIPT`,
   and `CONFIRM_EXPAND_MIGRATION` equal to that release ID. Export these securely;
   the script does not automatically load `.env`.
6. Rebuild/restart API, worker, and web through the existing production deployment
   procedure. Smoke-test login, student school edits, driver uploads, both route
   directions and capacity, all role-specific views, and manager Excel export.

Do not downgrade the database to roll back application code. Cross-school assignments
and paired-driver invariants need particular review before rolling back to v1.1.
